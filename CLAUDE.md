# CLAUDE.md — правила репозитория (для людей и агентов)

Этот файл — закон проекта. Любой агент (architect/coder/qa/art/content) и человек,
работая в репозитории, обязаны соблюдать эти правила. Нарушение = технический долг.

Игра: **свой Вальхейм в тёплом живом мире «доброго Kenshi»** (Alpine-старт).
Полные документы — в `docs/`. Метод мышления — **FPF** (First Principles Framework).

---

## 0. Три вещи, которые нельзя нарушать

1. **Не вширь, а вглубь.** Сначала одно взаимодействие до удовольствия, потом второе. Прошлый проект снесли за нарушение этого правила.
2. **Ядро игры не знает про Unity.** `MonoBehaviour` — деталь визуализации, а не место для логики.
3. **Ни строчки кода вслепую.** Всё проходит пайплайн Research → Design → Plan → Implement с гейтами.

---

## 1. FPF-дисциплина (метод мышления)

FPF — становой хребет проекта. Практически это значит:

- Различай **вещь / описание / решение / работу**: дизайн-док — не механика; задача в Jira — не сделанная работа.
- **Не схлопывайся рано:** держи варианты живыми, пока сравнение не ясно.
- **Скажи, что значит «лучше», до оптимизации** (назови характеристики: fps, уют, читаемость, стоимость API).
- **Доверие = доказательство + свежесть + область.** «Работает» подтверждается сборкой/тестом, не ощущением.
- Каждый проход оставляет **один полезный результат** (уточнённый вопрос, имя, сравнение, разрыв, безопасный документ).

Спека FPF приложена в Project-доках; имена паттернов вводим, только когда они делают решение точнее.

## 2. Пайплайн: Research → Design → Plan → Implement

Ни одна фаза не начинается, пока предыдущая не закрыта своим критерием.

- **Research** → артефакт `research_result.md`: как есть (As-Is), зависимости, варианты. Ни кода, ни планов.
- **Design** → Design Document (сущности, Use Cases, порты, инварианты). Ревью агентом-критиком.
- **Plan** → атомарные шаги с порядком файлов и критериями гейтов.
- **Implement** → код строго по плану, каждый шаг проверяем (batchmode-сборка + юнит-тест ядра).

Каждая задача в Jira несёт метку фазы и свой **Gate**.

## 3. Clean Architecture — закон кода

Сборки (asmdef), зависимости строго внутрь:

```
Game.Domain      — Rich Entities + события. БЕЗ using UnityEngine.
Game.Application — Use Cases, порты, Event Bus. Зависит только от Domain.
Game.Unity       — адаптеры, презентеры, View. Зависит от обоих + UnityEngine.
Game.Tests       — headless-тесты Domain+Application, без графики.
```

- **Rich Entities, не анемичные.** Поля приватны/init-only; менять — только методами, которые защищают инварианты (`ApplyDamage`, `AddItem`). Правило: если бизнес-правило могло существовать в 1800-х, оно внутри сущности.
- **Координаты — `System.Numerics.Vector3`** или свой struct, не `UnityEngine.Vector3`, в Domain/Application.
- **Игрок = ИИ.** Оба действуют через одни Use Cases. Расхождение поведения = архитектурная ошибка.
- **События публикуют Use Cases**, не сущности. Реакции — независимые подписчики (эмерджентность).
- **Расчёты вне Unity.** Никакого урона/экономики в `Update`/`OnCollisionEnter`. Физика — только сенсор.
- **`HP<0 → Destroy`** — прерогатива презентера, не домена.

---

## 4. Quality Gates (без них не принимается)

1. **Dependency Audit** — ноль `UnityEngine/UnityEditor/TMPro` в Domain/Application.
2. **Logic Integrity** — ХП/ресурсы не меняются в обход методов сущности.
3. **Headless Testing** — механики и циклы ИИ покрыты юнит-тестами, проходят без графики.
4. **AI Consistency** — один Use Case → идентичное поведение игрока и NPC.
5. **Feel** — срез реально приносит удовольствие.

## 5. Поток работы через Jira (проект SCRUM «GAME-DEV»)

- Эпик → Истории → Задачи. Каждая задача = фаза + Gate.
- Роли-метки: `architect` (Design-ревью), `coder` (Implement), `qa` (гейты сборки/тестов), `art` (сцены/свет/ассеты), `content` (NPC/диалоги/сюжет).
- **Реализация в изоляции** (ветка/worktree). Agent НЕ мёржит в `main` сам: сначала QA-агент (batchmode + тесты), потом ревью Principal (Юра).
- Переход Design→Plan→Implement аппрувит Principal.

## 6. Unity-специфика (грабли, уже оплаченные)

- Unity **6000.5.3f1** (6.5), URP. TMP/uGUI встроены — отдельно не ставить.
- **Серые модели Synty** лечит `Editor/SyntyMaterialFixer` (обязателен до любой работы со сценой).
- `UnityEngine.EntityId` конфликтует с нашим `EntityId` — using-алиас. `Physics.BakeMesh` требует `mesh.GetEntityId()`.
- **Bloom требует включённого HDR** в URP.
- **Процедурная расстановка = пустота** (проверено дважды). Мир — вживлять авторские сцены Synty + плотные осмысленные кластеры.
- Паки Synty (~4.4 ГБ) **не в git** (см. `.gitignore`) — копировать/переимпортировать отдельно.
- Проверка сборки без GUI: `Unity.exe -batchmode -quit -projectPath <путь> -executeMethod <NS>.ProjectSetup.Setup -logFile <лог>`.

## 7. Свет и композиция (метод Synty, для `art`)

Тёплый золотой час: солнце (1, 0.77, 0.48) I=1.2; тёплый туман (1, 0.83, 0.62) линейный 5→500; прохладный сиреневый ambient; Bloom+Vignette умеренно (HDR вкл). Плотность экстремальная (инстансинг+LOD), кластеры по смыслу, рамки кадра деревьями/хребтами. Каждый кадр — открытка.
