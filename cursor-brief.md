## Метод (нарушать нельзя)
1. **Пайплайн Research → Design → Plan → Implement.** Никакого кода вслепую. Сначала короткий план, потом код.
2. **Clean Architecture.** Три сборки, зависимости строго внутрь:
   - `Game.Domain` — Rich Entities + доменные события. **БЕЗ `using UnityEngine`.**
   - `Game.Application` — Use Cases, порты, Event Bus. Зависит только от Domain.
   - `Game.Unity` — адаптеры/презентеры/View (позже, когда будет Unity-проект).
   - `Game.Tests` — headless-тесты Domain+Application, без графики.
3. **Rich Entities, не анемичные.** Поля приватные/init-only; менять — только методами, защищающими инварианты. Координаты — `System.Numerics.Vector3`, не `UnityEngine.Vector3`.
4. **Игрок = ИИ:** любое действие проходит через Use Case; игрок и NPC вызывают одни и те же Use Cases.
5. **События публикуют Use Cases, не сущности.**
6. **Quality Gates:** (a) ноль ссылок на UnityEngine в Domain/Application; (b) инварианты нельзя обойти; (c) всё покрыто юнит-тестами, проходящими без Unity.

## Задача №1 (Crawl — маленькая, чтобы замкнуть цикл)
Создай .NET-решение для ядра и первую сущность с тестом:
1. Solution с проектами `Game.Domain` (classlib), `Game.Application` (classlib, ссылается на Domain), `Game.Tests` (xUnit, ссылается на оба). Target — актуальный .NET (net8.0+).
2. В `Game.Domain` — Rich Entity `Inventory`: приватные данные, вместимость/вес, методы `AddItem`/`RemoveItem`, защищающие инварианты (нельзя уйти в минус, нельзя превысить вместимость). Нарушение → доменное исключение.
3. В `Game.Tests` — юнит-тесты на инварианты (успешное добавление; отказ при переполнении; отказ при удалении отсутствующего).
4. Проверь `dotnet build` и `dotnet test` — оба зелёные.

Критерий приёмки: решение собирается, тесты проходят, в Domain нет `using UnityEngine`.
