# 03 · Архитектурный дизайн ядра — Clean Architecture для Unity

> Первый Design Document пайплайна (фаза Design). Проектирует **изоляцию логики игры от Unity**
> и эмерджентный живой мир, где игрок и ИИ равны перед правилами.
> Всё привязано к твоему реальному коду из архива (док 00) — не общая теория.

---

## 0. Главный тезис

`MonoBehaviour` — это деталь. Ядро игры (правила мира, экономика, крафт, стройка, ИИ-решения) живёт в **чистом C#**, ничего не знает про Unity и **тикает независимо от FPS**. Unity сидит на самом внешнем слое и только *рендерит* то, что уже произошло в ядре.

Хорошая новость: твой архивный код уже наполовину такой. `GameState.cs` — чистый POCO. `Commands.cs` — шина Validate+Apply. `WorldApi.cs` — статический фасад. Мы это **формализуем и делаем законом**, а не изобретаем заново.

---

## 1. Четыре слоя и правило зависимостей

Зависимости направлены **только внутрь**. Внешний слой знает про внутренний, никогда наоборот.

```
┌─────────────────────────────────────────────────────────┐
│  4. FRAMEWORKS & DRIVERS — Unity                          │
│     MonoBehaviour-виджеты, рендер, физика, ввод, аудио     │
│  ┌───────────────────────────────────────────────────┐   │
│  │  3. INTERFACE ADAPTERS — порты/адаптеры/презентеры  │   │
│  │     WorldApi (фасад), presenters, input-адаптеры    │   │
│  │  ┌─────────────────────────────────────────────┐   │   │
│  │  │  2. USE CASES — интеракторы (командная шина)  │   │   │
│  │  │     ChopTree, PlaceWall, Craft, Attack, TalkTo │   │  │
│  │  │  ┌───────────────────────────────────────┐   │   │   │
│  │  │  │  1. DOMAIN — Rich Entities + инварианты │   │   │   │
│  │  │  │     Inventory, Structure, Character,    │   │   │   │
│  │  │  │     Economy, WorldState, Genome         │   │   │   │
│  │  │  └───────────────────────────────────────┘   │   │   │
│  │  └─────────────────────────────────────────────┘   │   │
│  └───────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

**Закон:** Domain не импортирует `UnityEngine`. Use Cases не импортируют `UnityEngine`. Только слои 3–4 видят Unity. Проверяется механически (asmdef-сборки без ссылки на UnityEngine у слоёв 1–2).

## 2. Слой 1 — Domain: Богатые сущности (Rich Entities)

Классы, которые **сами защищают свои инварианты**. Данные приватны; менять их можно только методами, которые проверяют правила. Никаких публичных сеттеров, никаких «анемичных» структур, которыми крутит кто угодно.

| Сущность | Инвариант, который она держит | Опора в архиве |
| --- | --- | --- |
| `Inventory` | Количество ресурса не уходит в минус; вместимость не превышается | `InventoryService`, `ItemRegistry` |
| `Structure` / `BuildingPiece` | Деталь не висит в воздухе; стыкуется по правилам; требует ресурсов | писать новое (стройки нет) |
| `Character` (игрок и NPC) | ХП в границах; мёртвый не действует; экипировка валидна | `CharacterSpec`, `Genome`, `Phenotype` |
| `Economy` | Баланс сходится; цена = f(спрос/предложение); нет отрицательных запасов | писать новое (Market-биржу не тащим) |
| `WorldState` | Время монотонно; погода детерминирована от (seed, day) | `GameState`, `WorldClock`, `WeatherSystem` |
| `RecipeBook` / `CropPlan` | Рецепт применим только при наличии входов; стадии роста по порядку | `RecipeRegistry`, `CropRegistry` |

`GameState` остаётся корневым чистым POCO — «файл на поток состояния». Rich Entities живут внутри него.

---

## 3. Слой 2 — Use Cases: дирижёры механик (= твоя командная шина)

Каждое осмысленное действие мира — изолированный интерактор. Он не знает про коллизии и рендер. Он принимает простой **DTO** (контракт), обращается к нужным Rich Entities, применяет правило и возвращает результат + публикует событие.

**Твой `Commands.cs` (Validate + Apply) — это ровно оно.** Мы его продолжаем: `Validate` = проверка предусловий на Rich Entities, `Apply` = изменение состояния + эмиссия события.

Примеры: `ChopTreeUseCase`, `PlaceWallUseCase`, `CraftItemUseCase`, `AttackTargetUseCase`, `TalkToUseCase`, `PlantCropUseCase`.

### Унификация акторов: Игрок = ИИ

Механике всё равно, кто её вызвал. Клик игрока → Unity формирует DTO → `ChopTreeUseCase`. Решение NPC добыть дерево → тот же `ChopTreeUseCase`. **Один код правил на обоих.** Отсюда честная эмерджентность: вырубят весь лес — дровосеки-NPC через свой `Observe` увидят отсутствие ресурса и пойдут искать другое. Никто это не скриптовал.

---

## 4. Эмерджентность через события (Event-Driven)

Последствия действий не хардкодятся. Use Case только **публикует факт**, а автономные системы сами реагируют.

```
KillEntityUseCase(victim: Trader)
   └─ публикует  EntityKilledEvent(victim: Trader)
        ├─ Economy слышит → приток железа падает, цены растут
        ├─ Guard-система слышит → игрок в розыск (если жертва мирная)
        └─ Social-система слышит → родня скорбит, GraveViews ставит могилу
```

Системы договариваются через шину событий (Pub/Sub, хореография), а не прямыми вызовами. Это делает мир расширяемым: новая система просто подписывается на нужные события, не трогая старые (столп «фичи не ломают друг друга»). `GraveViews` из архива — первый готовый подписчик на «смерть».

---

## 5. Слой 3 — Interface Adapters: порты, адаптеры, презентеры

- **`WorldApi`** — фасад/порт: единственная дверь, через которую Unity-слой дёргает Use Cases и читает состояние. Уже есть в архиве.
- **Presenters** — Unity-виджеты подписываются на доменные события и обновляют картинку. Domain сказал `StructurePlacedEvent` → презентер заспавнил префаб через `AssetLibrary` (семантический ключ, а не путь).
- **Input-адаптеры** — `InputRouter` (режимы: пешком/UI/диалог) переводит ввод в DTO для Use Cases.
- **`AssetLibrary` + `AssetMap`** — мост «семантический ключ → префаб Synty» с откатом на примитив. Ядро оперирует смыслом («дерево лиственное среднее»), адаптер выдаёт конкретный меш.

---

## 6. Слой 4 — Unity как визуализатор

MonoBehaviour-компоненты только рендерят и ловят ввод: рендер, физика/коллизии, аниматоры (Humanoid-ретаргет работает на всех), частицы, аудио. Вся логика — уже случившаяся в ядре. `SyntyMaterialFixer` живёт здесь же (editor-время), чинит серые материалы.

---

## 7. In-game AI: цикл Observe → Reason → Action

NPC — не бот, бегущий к точке, а агент с тактом ORA. **Action всегда = вызов тех же Use Cases.**

- **Observe.** Каждый такт агент читает *локальное* состояние вокруг себя (ближайшие Rich Entities), кладёт в короткую память. Контекстная инженерия: агент видит не весь мир, а окрестность. Опора: `NpcBrain`, `NpcTicker`, `NpcWorld`.
- **Reason.** По данным принимает решение:
  - **Дёшево (мобы, рядовые NPC):** дерево поведений / utility-AI. Не жжём API.
  - **Дорого (важные сюжетные NPC, «Правитель фракции»):** LLM для долгих планов («хочу захватить соседний город»). Строго дозированно.
- **Action.** Выбирает инструмент (Tool) из доступных. Инструменты = Use Cases. Значит, всё, что может NPC, может и игрок, и наоборот.

---

## 8. Память мира (State Management)

- **Short-term (оперативка).** Текущее состояние — обычные C#-объекты (Rich Entities), изолированы от Unity. Быстро, тестируемо.
- **Long-term (RAG) — только для глобальных LLM-агентов.** Факты о мире записываются («игрок 10 ч назад сжёг ферму фракции»). Когда «Правитель» генерит план через LLM, нужный факт достаётся через retrieval и кладётся в контекст → «ты сжёг мои посевы — уничтожу твою базу». Так мир *помнит*, не раздувая контекст LLM до всего мира сразу. Это же — рычаг контроля бюджета API.

---

## 9. Детерминизм и headless-тик (независимость от FPS)

Экономика и ИИ считаются **асинхронно, не в кадре**. Unity рендерит результат. Опора: `WorldClock` (сутки за 20 мин), `WeatherSystem` (детерминированная погода от seed+day). Поскольку ядро чистое и детерминированное:

- мир может **тикать без игрока** (жизнь продолжается — свойство Kenshi);
- **всю экономику, крафт и ИИ можно тестировать без запуска редактора** — гоняем ядро в обычном C#-тесте/batchmode. Это и есть суперсила чистой архитектуры.

Сохранения: сериализуем `GameState` (POCO) через `SaveService`. Никаких MonoBehaviour в сейве — только чистое состояние.

## 10. Карта: слой → что берём из архива

| Слой | Берём готовое | Пишем новое |
| --- | --- | --- |
| Domain | `GameState`, `Genome`, `Phenotype`, реестры (Item/Recipe/Crop/Animal), `WorldClock`, `WeatherSystem` | `Structure`/строительство, `Economy` |
| Use Cases | `Commands` (Validate+Apply) как основа | конкретные интеракторы + шина событий |
| Adapters | `WorldApi`, `AssetLibrary`+`AssetMap`, `InputRouter`, презентеры UI | презентеры под новые механики |
| Unity | UI-каркас, иконки, `AmbienceController`, `DayNightController`, `PhotoMode`, `AdminPanel`, `SyntyMaterialFixer` | движение+камера (пишем заново) |
| AI | `NpcBrain`, `NpcTicker`, `NpcWorld`, `Dialogue`, `GraveViews` | слой ORA-целей, BT/utility, RAG для LLM-агентов |

---

## 11. Тестируемость (критерий качества)

Правило: **любую механику ядра можно проверить без Unity.** Тест поднимает `GameState`, дёргает Use Case через DTO, проверяет инвариант и событие. Пример: «вырубить дерево при пустом инвентаре → инвентарь +1 бревно, опубликован `TreeChoppedEvent`, ХП дерева = 0». Ноль обращений к `UnityEngine`.

---

## 12. Мост к фазе PLAN — с чего программируем

Как архитектор — настаиваю: **сначала чистое ядро доменных моделей, потом Unity.** Порядок файлов (это уже задел следующего дока «Implementation Plan»):

1. `GameState` + корневые Rich Entities (`Inventory`, `WorldState`) — перенос из архива, очистка от Unity.
2. Шина Use Cases (`Commands`) + шина событий.
3. Первые интеракторы среза «Первая ночь»: `ChopTree`, `PlaceWall`, `TalkTo`.
4. Тесты ядра на эти интеракторы (без редактора).
5. Адаптеры: `WorldApi`, презентеры + `AssetLibrary`.
6. Unity-слой: движение/камера заново, вживление авторской сцены, свет золотого часа.
7. ORA-слой для одного NPC (Observe→Reason(BT)→Action через Use Cases).

Каждый шаг проверяем (компиляция batchmode + тест ядра) и имеет критерий готовности. Детальный план с критериями — отдельный документ фазы PLAN.

---

## 13. Что осталось решить (открытые вопросы Design)

- Формат DTO и шины событий (простые struct + типизированные события vs единый message-bus).
- Где проходит граница «дёшево BT / дорого LLM» — какие NPC вообще получают LLM.
- Формат long-term памяти для RAG (лог фактов + эмбеддинги vs проще на старте).
- Гранулярность тика ядра (фикс-степ симуляции vs событийный).
