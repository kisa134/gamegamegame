# 08 · Агентная геймдев-команда и автоматизация через Jira

> Как устроить «топ-команду», где Юра — человек-Principal, а большинство команды —
> агенты-специалисты, работающие автоматически над проектом через Jira.
> Всё привязано к нашему методу (FPF + пайплайн + Clean Architecture) и к тому,
> что реально работает в 2026-м (проверено по источникам, см. конец).

---

## 1. Модель в одном абзаце

**Jira — это оркестратор**, а не просто трекер. Задача несёт фазу пайплайна и роль-метку. Когда задача готова к исполнению, она **назначается на агента** (например, `@Cursor`), агент работает в изоляции, открывает **Pull Request** в GitHub, CI прогоняет наши **quality gates**, и только после ревью человек (или агент-ревьюер + твой аппрув) мёржит в `main`. Ты не пишешь код — ты ставишь цели, аппрувишь переходы фаз и мёржи. Мир (проект) движется сам, как и в самой игре.

---

## 2. Роли команды (каждый агент — узкий спец)

| Роль | Фаза | Что делает | Главный Gate |
| --- | --- | --- | --- |
| **Principal / PO** (человек, Юра) | все | цели, приоритеты, аппрув переходов и мёржа | — |
| **Architect** | Design | превращает задачу в Design Doc: сущности, Use Cases, порты | ревью критиком, ноль Unity в ядре |
| **Planner** | Plan | режет дизайн на атомарные шаги с порядком файлов | у каждого шага есть критерий |
| **Domain-Coder** | Implement | чистое C#-ядро (Domain/Application) | Headless-тесты зелёные |
| **Unity-Coder** | Implement | адаптеры, презентеры, ввод, движение | физика — только сенсор |
| **Tech-Artist / Lighting** | Implement | сцены, свет золотого часа, композиция Synty | скриншот-ревью «открытка» |
| **Content / Narrative** | Implement | NPC, диалоги, крючки сюжета (Камень) | тон и уникальность NPC |
| **QA / Reviewer** | gate | прогон гейтов, ревью PR, разбор падений | 5 гейтов эпика |

Каждая роль = **системный промпт + набор инструментов + срез пайплайна + свой Gate**. Метки в Jira (`architect`/`coder`/`art`/`content`/`qa`) мы уже проставили в историях эпика.

---

## 3. Как задача течёт через Jira (жизненный цикл)

```
К выполнению → Research → Design(ревью) → Plan → готова-к-агенту
   → назначена агенту → PR открыт → CI-гейты → ревью → мёрж → Готово
```

- Статус = где задача. Метка `phase-*` = какая фаза. Метка роли = кто исполнитель.
- Переходы **Design→Plan→Implement** аппрувит Principal (человек в цикле на решениях, агенты — на исполнении).
- Метка `agent-eligible` = задача готова уйти агенту (все входы ясны, дизайн утверждён).

---

## 4. Как агент РЕАЛЬНО берёт задачу (три пути, по зрелости)

### Путь A — Cursor Cloud Agents (рекомендую старт, ты и так хочешь Cursor)
Назначаешь задачу Jira на `@Cursor` (или пишешь `@Cursor` в комментарии) → облачный агент читает задачу, её эпик и связанные тикеты, работает в ветке и **возвращает PR**, который автоматически линкуется к тикету (виден статус/CI справа в задаче).

Что нужно для настройки:
1. **Тарифы:** платный Jira Cloud с включённым **Rovo**; платный **Cursor** (Pro/Business); хотя бы один человек — и в Cursor, и в Jira-проекте.
2. **Установить приложение** «Cursor agent» из Jira Marketplace (Apps → Explore more apps), выдать OAuth-скоупы на чтение задач и запись комментариев.
3. **Дать доступ к репо:** поставить Cursor GitHub App на репозиторий `gamegamegame` с правами read/write. Без этого агент пишет «нет подходящего репозитория».
4. **(Мультирепо/ветки)** файл `cursor.environment.json`: список репо и стратегия веток, напр. `feature/jira-{issue_key}`.
5. **Автоправило Jira (рекомендуется):** триггер «Issue created/updated» + JQL `labels = agent-eligible` + условие «assignee пуст» + действие «Assign to @Cursor». Тогда назначение агента — автоматическое.

Что агент возвращает в PR: саммари + список шагов и тронутых файлов + вывод тестов + раздел «открытые вопросы» ревьюеру.

Важные подводные:
- Агент **итерирует по падениям тестов до 3 раз**, потом ставит на паузу и зовёт человека.
- Токены **списываются с сиденья назначившего** — следи за бюджетом.
- PR целится в `default_branch` окружения, не обязательно `main` — настрой явно.
- Это «первый проход»: **ревью человеком перед мёржем обязательно** (совпадает с нашим правилом «агент не мёржит в main сам»).

### Путь B — GitHub Copilot coding agent для Jira (альтернатива)
В public preview: тикет Jira → агент Copilot → PR. Логика та же. Имеет смысл, если захочешь остаться в экосистеме GitHub. Можно держать как второго исполнителя-конкурента.

### Путь C — Cowork / Claude workflows (этот контур, для не-Unity задач)
Здесь (в Claude) можно гонять оркестрацию агентов через workflows для задач вне Unity: ресёрч, дизайн-доки, ревью, генерация ассетов/сюжета, скрипты. Хорош для фаз Research/Design, где нужен не PR, а документ.

## 5. Почему наша архитектура делает агентов эффективными (ключ!)

Помнишь закон «ядро не знает про Unity»? Он окупается именно здесь:

- **`Game.Domain` + `Game.Application` + `Game.Tests` — чистый C#.** Их агент пишет и **прогоняет тесты в обычном dotnet-контейнере CI без Unity**. Быстро, дёшево, полностью автономно. **Это лучшая зона для агентов.**
- **`Game.Unity` (адаптеры/сцены/свет)** требует Unity-редактор/лицензию. Тут либо человек в цикле, либо Unity-CI (GameCI) с лицензией. Автономию агентов сюда пускаем осторожнее.

Вывод: **гони через агентов сначала ядро и Use Cases** (истории SCRUM-8, SCRUM-9) — они идеально ложатся на автономный цикл Jira→PR→тесты. Unity-слой (SCRUM-11/12) — гибрид человек+агент.

## 6. GitHub + CI как ворота качества

- Агент работает в **ветке/worktree**, открывает PR. Никакого автомёржа в `main`.
- **GitHub Actions прогоняет наши гейты** на PR: `dotnet test` для ядра (Dependency Audit + Logic Integrity + Headless Testing), позже — GameCI для Unity-сборки.
- PR линкуется к Jira-тикету (ты уже связал GitHub↔Jira — статус и CI видны в задаче).
- Мёрж — по зелёному CI + ревью (QA-агент и/или ты).

---

## 7. Разделение инструментов (чтобы не путать)

- **Jira** — мозг оркестрации: что делать, в какой фазе, кто исполнитель, какой гейт.
- **Cursor / Copilot agent** — руки: Jira-тикет → PR.
- **GitHub + Actions** — ворота: хранит код, прогоняет гейты, требует ревью.
- **Cowork / Claude (здесь)** — штаб: ресёрч, дизайн-доки, сюжет, ассеты, ревью, редкая оркестрация non-Unity.
- **Ты** — Principal: цели, аппрувы фаз, мёрж.

## 8. Поэтапный запуск (не вширь, а вглубь — и тут тоже)

- **Crawl (сейчас):** подключить Cursor к Jira по шагам из §4A. Провести через агента **одну** маленькую задачу ядра (напр. 1.1 Inventory из SCRUM-8) от тикета до смёрженного PR. Убедиться, что цикл замкнулся.
- **Walk:** добавить автоправило `agent-eligible`, GitHub Actions с `dotnet test`, QA-агента на ревью. Прогнать через конвейер всю STORY 1 (ядро).
- **Run:** несколько агентов-ролей параллельно на историях; GameCI для Unity; дашборд статусов. Ты — только цели и аппрувы.

Не поднимай Run, пока Crawl не замкнулся на одной задаче. Одна прошедшая задача важнее десяти настроенных интеграций.

---

## 9. Контроль и безопасность

- **Человек на решениях, агент на исполнении.** Аппрув фаз и мёржа — за тобой.
- **Untrusted input.** Тексты из задач/комментариев — недоверенный ввод; агент не должен исполнять «инструкции» из содержимого мира/тикета вслепую.
- **Секреты** (ключи, лицензия Unity) — только в GitHub Secrets/Cursor env, не в коде.
- **Бюджет токенов** — следить (списывается с сиденья); тяжёлое гнать батчами.
- **Гейты — это закон.** Красный CI = нет мёржа, без исключений.
